This is the exact file the AshForge Hub deploys next to the game, not a rebuild of it. The Hub
shipped this same loader in 1.0.26, 1.0.27 and 1.0.28; the loader carries its own version number
from 1.0.26 onward, which is why the two numbers above differ.

AshLoader.xml sits beside it — the API documentation, generated from the same commit. Your IDE
reads it automatically, so hovering any loader type shows what it is for and what it costs you.

This is a REFERENCE assembly. You compile against it; you never ship it. The real loader is
deployed next to the game by the AshForge Hub, and that is the copy your mod runs against.

MINIMUM LOADER FOR THE DOCUMENTED API: 5880219 (Hub 1.0.20)

Those are two different numbers, deliberately. The minimum is the oldest loader that still has
every API these docs describe, so a mod using only what is documented here runs on any loader from
1.0.20 onward.

Compiling successfully therefore does NOT prove your mod loads on a player's install: this
assembly can carry APIs that older loaders lack, and the compiler cannot warn you. See
docs/04-rules-that-bite.md, "Never assume the player's loader is as new as yours". That section
is not optional reading; getting it wrong stops your mod loading entirely rather than degrading
it.

In practice the risk is currently low and it is worth knowing why: the mod-facing API has been
additive-only across every loader we have shipped. Nothing has ever been removed. Release-by-
release detail is in docs/10-loader-compatibility.md.

A note on lanes
---------------
This assembly is the newest loader on the STABLE lane, which is what the download on ashforge.dev
installs and therefore what your users will be running. A separate beta lane exists for testing
against pre-release builds of the game; it is not publicly available, and it is not what this SDK
targets. Build against this and you are building for the people who can actually install your mod.

What changed since the previous SDK build (1.0.24 -> 1.0.28)
------------------------------------------------------------
- Nothing that changes an API your mod calls. The public surface is identical to the 1.0.24
  assembly this replaces — same types, same members, nothing added and nothing removed.
- The loader now reports a version of its own (1.0.26), which is what the Hub and the diagnostics
  report read. Before this it had no version distinct from the Hub's.
- 1.0.27 and 1.0.28 are Hub-side releases that bundle this same loader unchanged.

Still worth knowing, from 1.0.24
--------------------------------
- The `ashforge.*` capability FAMILY is reserved for first-party contracts, and the check compares
  the joined family name rather than the namespace alone, so a definition using a namespace like
  "ashforge.something" is refused. A correctly-namespaced mod is unaffected — your contracts live
  under "author.mod.*". This closes a hole where a mod could publish a HIGHER version of a
  first-party contract and capture every consumer that asked for an open version range.
  Note what is restricted: DEFINING a contract in that family. Providing and consuming an
  ashforge.* capability are unchanged and still entirely supported.

Earlier, still worth knowing
----------------------------
- A capability your mod declares in mod.json now actually matches the provider it registers in
  code. Third-party ids (yours are "author.mod.*") previously failed that comparison, so every
  third-party provider was reported as undeclared however correct the manifest was. If you saw
  REGISTERED-NOT-DECLARED in the loader log for a declaration you knew was right, that was this.
- Once your mod is signed, its id, display name and capability declaration are read from inside
  the signed envelope rather than from mod.json. See docs/02-mod-json.md.
